# CIL ↔ Project LEE Integration Specification

*From the Project LEE side — what CIL needs to implement to accept LEE as a client.*
*Version 1.1 · September 2026*

---

## Overview

Project LEE is the operating intelligence layer in the Lamont Labs stack. She calls CIL through a `ReasoningService` interface before any model execution. CIL is the mandatory cognitive-routing authority: it decides whether the request is satisfied by T1/T2 reuse or whether an approved T3 model route may execute. The goal is cost reduction through reuse: if CIL has an approved cognitive asset that resolves the query, LEE never calls a model at all.

LEE calls CIL for **informational and reasoning requests only** — summarizing, explaining, analyzing, synthesizing. She does not call CIL for consequential actions (those go to CerbaSeal).

LEE and CIL maintain **independent databases**. LEE never accesses CIL's database directly. All interaction is through the versioned API described in this document.

---

## What LEE needs from CIL

1. One authenticated HTTP endpoint that accepts a structured query package from LEE
2. A structured response that includes resolution tier, answer, reuse metadata, and cost
3. A service identity and credential system LEE can authenticate against
4. Graceful 4xx/5xx error responses (LEE enters explicit no-model or held reasoning when CIL is unavailable)

---

## Endpoint

```
POST /query/lee
```

This is a LEE-specific enriched endpoint alongside CIL's existing `/query` base primitive. The existing `/query` route stays unchanged. LEE uses `/query/lee` when it needs the richer response metadata (resolution tier, asset version, drift detection, etc.).

If a dedicated endpoint is premature, LEE can call the existing `/query` route and tolerate a subset of the response fields — see the compatibility note at the end.

---

## Request Schema

LEE sends a `CILQueryRequest` object. All fields are required unless marked optional.

```typescript
interface CILQueryRequest {
  // Identity
  correlation_id: string;            // UUID generated by LEE; echoed in response
  lee_brain_version: string;         // e.g. "2026.7.1" — for CIL's audit trail
  source_context_checksum: string;   // SHA-256 of the context packet LEE used to build this query

  // The query
  query_text: string;
  semantic_domain: string;           // e.g. "governance", "product", "technical", "relationship"

  // Intent context (from LEE's Intent Engine)
  intent: {
    intent_type: string;             // e.g. "EXPLANATION", "SYNTHESIS", "ANALYSIS", "RETRIEVAL"
    risk_classification: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL";
    project_id?: string;             // Lamont Labs project identifier, when relevant
  };

  // Context references (not full content — just IDs LEE used to build the query)
  context_asset_refs: string[];      // LEE object IDs included as context for this query

  // Quality requirements
  freshness_requirement: "any" | "current" | "verified";

  // Permissions
  reuse_permitted: boolean;          // whether a cached/reused asset may satisfy this query
  frontier_escalation_permitted: boolean; // whether CIL may escalate to frontier if no asset found

  // Budget
  desired_format: "concise" | "detailed" | "structured" | "narrative";
  cost_ceiling_usd?: number;         // optional hard ceiling; CIL should reject gracefully if exceeded
}
```

**Example:**
```json
{
  "correlation_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "lee_brain_version": "2026.7.1",
  "source_context_checksum": "sha256:abc123...",
  "query_text": "Explain CerbaSeal's pilot model in simple terms for a general audience.",
  "semantic_domain": "governance",
  "intent": {
    "intent_type": "EXPLANATION",
    "risk_classification": "LOW",
    "project_id": "cerbaseal"
  },
  "context_asset_refs": ["fact:cerbaseal-pilot-structure", "interp:cerbaseal-summary"],
  "freshness_requirement": "current",
  "reuse_permitted": true,
  "frontier_escalation_permitted": true,
  "desired_format": "narrative",
  "cost_ceiling_usd": 0.05
}
```

## Response Schema

CIL returns a `CILQueryResponse`. All fields are required unless marked optional.

```typescript
interface CILQueryResponse {
  // Identity
  correlation_id: string;            // echoed from request

  // Resolution
  resolution_tier: "T1_TRIGRAM" | "T2_SEMANTIC" | "T3_FRONTIER";
  answer: string;

  // Reuse metadata (present for T1 and T2)
  cognitive_asset_id?: string;       // ID of the reused cognitive asset
  asset_version?: string;            // version of the asset used
  governance_status?: "approved" | "nominated" | "unreviewed";

  // Quality signals
  confidence: number;                // 0–1
  freshness_state: "fresh" | "current" | "stale" | "expired";
  drift_detected: boolean;           // true if asset content appears to conflict with recent context
  contradiction_detected: boolean;   // true if asset contradicts another known asset
  reuse_eligible: boolean;           // whether this response could itself become a cognitive asset

  // Escalation
  recommend_escalation: boolean;     // CIL recommends frontier escalation despite returning an answer
  escalation_reason?: string;

  // Cost and performance
  cost_usd: number;
  latency_ms: number;

  // Provenance
  provenance: string[];              // source references CIL used (asset IDs, document refs, etc.)
  semantic_domain: string;          // echoed from request
}
```

**Example:**
```json
{
  "correlation_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "resolution_tier": "T2_SEMANTIC",
  "answer": "CerbaSeal's pilot model works by...",
  "cognitive_asset_id": "asset:cerbaseal-pilot-explanation-v3",
  "asset_version": "3",
  "governance_status": "approved",
  "confidence": 0.87,
  "freshness_state": "current",
  "drift_detected": false,
  "contradiction_detected": false,
  "reuse_eligible": false,
  "recommend_escalation": false,
  "cost_usd": 0.00,
  "latency_ms": 42,
  "provenance": ["asset:cerbaseal-pilot-explanation-v3"],
  "semantic_domain": "governance"
}
```

## Authentication

LEE authenticates to CIL using a **service identity credential** — a secret token issued to LEE by whoever administers CIL's access control.

**What CIL needs to implement:**

1. **A service identity for LEE** — a named credential with a defined permission scope:
   - `query:submit` — submit queries via POST /query/lee
   - `asset:nominate` (optional, for future LEE-initiated asset nomination) — nominate a reusable asset for governance review

   LEE should NOT be granted: policy modification, asset approval, asset deletion, user management.

2. **Request authentication** — CIL should validate each request using one of:
   - Bearer token in `Authorization` header (`Authorization: Bearer <token>`)
   - Short-lived JWT signed with a shared secret (preferred for production)
   
   LEE will include the token on every request. The token should have a TTL and be rotatable without downtime.

3. **Request signature (recommended for production):**
   CIL should validate an `X-LEE-Signature` header containing an HMAC-SHA256 of:
   ```
   HMAC-SHA256(secret, correlation_id + "." + timestamp + "." + body_sha256)
   ```
   This protects against replay attacks. LEE will include `X-LEE-Timestamp` alongside.

4. **Replay protection:**
   Reject any request where `correlation_id` has been seen in the past 10 minutes, or where `X-LEE-Timestamp` is more than 5 minutes old.

5. **Rate limits:**
   Apply per-credential rate limits to LEE's service identity. LEE should receive a `429 Too Many Requests` with a `Retry-After` header when rate-limited, not a silent drop.

**Credential delivery:**
CIL's administrator issues the credential out-of-band. LEE stores it as an environment secret — never in code, never in LEE's database.

## Error Responses

LEE handles CIL errors gracefully. CIL should return standard HTTP error codes with a JSON body:

```typescript
interface CILErrorResponse {
  error_code: string;      // e.g. "COST_CEILING_EXCEEDED", "DOMAIN_NOT_SUPPORTED", "RATE_LIMITED"
  error_message: string;
  correlation_id: string;  // echoed from request if available
  retry_after_seconds?: number;  // for 429 responses
}
```

| HTTP Status | When to return |
|------------|----------------|
| 400 | Malformed request or missing required fields |
| 401 | Missing or invalid credential |
| 403 | Valid credential but insufficient scope |
| 422 | Request is valid but CIL cannot satisfy it (e.g. cost ceiling too low, domain unsupported) |
| 429 | Rate limit exceeded — include `retry_after_seconds` |
| 500 | Internal CIL error |
| 503 | CIL temporarily unavailable — include `retry_after_seconds` |

**On any 5xx or timeout:** LEE marks CIL as DEGRADED, refuses model execution for that request, and emits a `CILUnavailable` event into its own Event Log. LEE may still perform local extraction, context-only operations, or recovery work. It must not route directly to a frontier model.

**On model execution failure:** LEE sends the failed CIL-selected route and a bounded failure reason back to CIL as a new correlated reroute request. CIL selects the next permitted route. LEE's Model Router executes only that new CIL decision; it never chooses the replacement model or provider locally.

## What LEE Will Never Send

To be explicit about what CIL should not expect or accept from LEE:

- **Secrets or credentials** — never in query_text, context_asset_refs, or any field
- **Raw environment variable values** — LEE's constitutional constraint
- **LEE's full memory database** — LEE sends a scoped query, not a memory dump
- **Personal data beyond what is necessary for the query** — LEE scopes queries by project and domain

---

## What LEE Records on Its Side

After every CIL call, LEE records the following in its own Event Log (CIL does not need to do anything for this):

```
CILQueryRequested  — correlation_id, semantic_domain, project_id, risk_classification
CILQueryResolved   — correlation_id, resolution_tier, confidence, cost_usd, latency_ms
CILReuseHit        — correlation_id, cognitive_asset_id, asset_version, tier  (when T1 or T2)
CILFrontierEscalated — correlation_id, escalation_reason  (when T3)
CILDriftDetected   — correlation_id, cognitive_asset_id  (when drift_detected: true)
CILContradictionDetected — correlation_id, cognitive_asset_id  (when contradiction_detected: true)
CILUnavailable     — timestamp, error_summary, model_execution_blocked  (on 5xx / timeout)
```

These events stay in LEE's Event Log. They are not shared back to CIL.

| Domain | Description |

| `research` | Market, competitive, technical research topics |

## Compatibility Note: Existing /query Route

If implementing `/query/lee` immediately is not practical, LEE can call CIL's existing `/query` route using the subset of fields that already exist (`query_text`, `semantic_domain`). In that mode, LEE will not receive `cognitive_asset_id`, `asset_version`, `drift_detected`, `contradiction_detected`, or `freshness_state` — and it will treat every response as `reuse_eligible: false`.

This is a degraded integration mode — LEE works but cannot attribute reuse, track drift, or record asset provenance accurately. The `/query/lee` endpoint is the target state.

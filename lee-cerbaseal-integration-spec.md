# CerbaSeal ↔ Project LEE Integration Specification

*From the Project LEE side — what CerbaSeal needs to implement to accept LEE as a client.*
*Version 1.0 · July 2026*

---

## Overview

Project LEE is the operating intelligence layer in the Lamont Labs stack. Before executing any consequential action — sending an email, sharing a document, modifying a repository, contacting an investor — LEE submits a `GovernedRequest` to CerbaSeal and waits for a verdict.

LEE's behavior is **fail-closed**: if CerbaSeal is unavailable, the action does not execute. If the verdict is HOLD or REJECT, the action does not execute. There is no fallback execution path. CerbaSeal is the authorization boundary, not an advisory service.

LEE and CerbaSeal maintain **independent databases**. LEE never accesses CerbaSeal's database directly. All interaction is through the versioned API described in this document.

---

## What LEE needs from CerbaSeal

1. One authenticated HTTP endpoint that accepts a structured governed action request from LEE
2. A verdict response — ALLOW, HOLD, or REJECT — with reason codes, a decision ID, and an evidence bundle reference
3. A service identity and credential system LEE can authenticate against
4. Strict 4xx/5xx error responses — LEE places the action on HOLD on any non-200 response

---

## Endpoint

```
POST /govern/evaluate
```

LEE submits every consequential action to this endpoint. CerbaSeal evaluates the request against its configured policy packs, approval chains, authority classes, and action policies, then returns a verdict synchronously.

If CerbaSeal already has an equivalent evaluation endpoint, LEE can adapt to it — the field names in this document are LEE's preferred schema, but CerbaSeal's existing field names take precedence as long as the semantic meaning is preserved.

## Request Schema

LEE sends a `GovernedRequest` object. All fields are required unless marked optional.

```typescript
interface GovernedRequest {
  // Identity
  lee_request_id: string;            // UUID generated by LEE; echoed in response
  policy_pack_version: string;       // version of CerbaSeal's policy pack LEE expects to be evaluated against

  // The action being evaluated
  proposed_action: string;           // human-readable description of what LEE intends to do
  action_class: ActionClass;         // see Action Class Registry below
  workflow_class: string;            // maps to CerbaSeal's configured workflow — e.g. "external_communication"

  // Actor and target
  actor_identity: string;            // LEE's service identity name — e.g. "lee-service"
  target_system: string;             // the system where the action will occur — e.g. "gmail", "github", "google_drive"
  affected_project_id?: string;      // Lamont Labs project identifier, when the action concerns a specific project

  // Authority and approvals
  authority_class: string;           // authority class as defined in CerbaSeal's config — e.g. "OWNER", "SYSTEM"
  required_approvals: ApprovalSpec[];
  approvals_present: Approval[];     // approvals LEE has already collected before submitting

  // Action metadata
  reversibility: "reversible" | "partially_reversible" | "irreversible";
  data_sensitivity: "public" | "internal" | "confidential" | "restricted";
  expected_downstream_effect: string; // plain description of what happens if ALLOW is returned
  communication_recipient?: string;  // for EXTERNAL_COMMUNICATION actions — who will receive the message

  // Provenance and context
  intent_record_id: string;          // ID of LEE's typed Intent record that triggered this action
  source_provenance: string;         // how LEE decided this action was appropriate
  context_checksum: string;          // SHA-256 of the context packet LEE used to make this decision
  evidence_refs: string[];           // LEE object IDs (facts, interpretations, waiting loops) supporting the action

  // Trust and timing
  trust_state: "verified" | "nominal" | "degraded"; // current trust level of LEE's own subsystem
  requested_execution_window?: {     // optional — when the action should execute if allowed
    not_before: string;              // ISO 8601
    not_after: string;               // ISO 8601
  };
}

type ActionClass =
  | "EXTERNAL_COMMUNICATION"         // sending email, message, post
  | "EXTERNAL_DOCUMENT_SHARE"        // sharing a document with someone outside LEE
  | "REPOSITORY_MODIFICATION"        // push, merge, create branch in a connected repo
  | "DEPLOYMENT_CHANGE"              // trigger or approve a deployment
  | "MEMORY_DELETION"                // delete or overwrite important LEE memory objects
  | "FINANCIAL_TRANSACTION"          // any action involving money
  | "CANONICAL_STATUS_CHANGE"        // changing a project's official status
  | "CONNECTOR_PERMISSION_GRANT"     // granting a new connector permission
  | "SENSITIVE_DATA_EXPORT"          // exporting sensitive project data
  | "INVESTOR_PARTNER_CONTACT"       // contacting an investor or pilot partner
  | "CROSS_SYSTEM_WORKFLOW"          // executing a workflow in another Lamont Labs system
  | "PROVIDER_WRITE_ACTION";         // any write action through an external provider

interface ApprovalSpec {
  approver_role: string;
  required: boolean;
  reason: string;
}

interface Approval {
  approver_role: string;
  approver_identity: string;
  approved_at: string;               // ISO 8601
  approval_method: "explicit" | "implicit" | "delegated";
}
```

**Example — sending an email to a pilot partner:**

  "policy_pack_version": "2026.7.1",

## Response Schema

CerbaSeal returns a `GovernedResponse`. All fields are required unless marked optional.

```typescript
interface GovernedResponse {
  // Identity
  lee_request_id: string;            // echoed from request
  decision_id: string;               // CerbaSeal's stable identifier for this decision

  // The verdict
  verdict: "ALLOW" | "HOLD" | "REJECT";
  reason_codes: string[];            // machine-readable reason codes for HOLD or REJECT
  checked_invariants: InvariantResult[];

  // What is missing (for HOLD)
  missing_approvals?: ApprovalSpec[];
  remediation_requirements?: string[]; // what must happen before re-submission

  // Evidence and audit
  decision_envelope: string;         // CerbaSeal's stable, signed reference to this decision
  evidence_bundle_ref: string;       // reference to the evidence bundle CerbaSeal assembled
  audit_entry_ref: string;           // reference to the append-only audit log entry
  replay_checksum: string;           // checksum for independently verifying this decision

  // Policy
  policy_version: string;            // version of policy pack used for evaluation
  timestamp: string;                 // ISO 8601 — when CerbaSeal made the decision

  // Execution constraints
  authorization_expiry?: string;     // ISO 8601 — ALLOW verdicts may have an expiry window
  human_confirmation_required: boolean; // true if CerbaSeal requires explicit human confirmation before execution
}

interface InvariantResult {
  invariant_id: string;
  invariant_description: string;
  result: "passed" | "failed" | "not_applicable";
  failure_reason?: string;
}
```

## Authentication

LEE authenticates to CerbaSeal using a **service identity credential** issued by whoever administers CerbaSeal's access control.

**What CerbaSeal needs to implement:**

1. **A service identity for LEE** — a named credential with a tightly scoped permission set:
   - `govern:evaluate` — submit governed requests for evaluation via POST /govern/evaluate
   
   LEE must NOT be granted: policy pack modification, approval chain modification, decision record deletion, audit log access, user management.

   Policy modification must require a separate, higher-trust administrative credential — not LEE's.

2. **Request authentication:**
   - Bearer token in `Authorization` header (`Authorization: Bearer <token>`)
   - Short-lived JWT signed with a shared secret (preferred for production; TTL ≤ 5 minutes)

3. **Request signature (required for production):**
   CerbaSeal should validate an `X-LEE-Signature` header containing an HMAC-SHA256 of:
   ```
   HMAC-SHA256(secret, lee_request_id + "." + timestamp + "." + body_sha256)
   ```
   LEE includes `X-LEE-Timestamp` alongside. Reject requests where the timestamp is more than 5 minutes old.

4. **Replay protection:**
   Reject any request where `lee_request_id` has been seen before. CerbaSeal should permanently record every `lee_request_id` it processes — resubmission with the same ID is an error, not a retry signal. LEE generates a new `lee_request_id` for every new submission.

5. **Rate limits:**
   Apply per-credential rate limits. Return `429 Too Many Requests` with `Retry-After` — never a silent drop. Given the fail-closed nature of this integration, a rate limit should be treated as a temporary HOLD by LEE, not a rejection.

**Credential delivery:**
CerbaSeal's administrator issues the credential out-of-band. LEE stores it as an environment secret — never in code, never in LEE's database, never logged.

## Error Responses

CerbaSeal should return standard HTTP error codes with a JSON body:

```typescript
interface CerbaSealErrorResponse {
  error_code: string;          // e.g. "INVALID_ACTION_CLASS", "POLICY_PACK_VERSION_MISMATCH", "RATE_LIMITED"
  error_message: string;
  lee_request_id: string;      // echoed from request if available
  retry_after_seconds?: number; // for 429 responses
}
```

| HTTP Status | When to return | LEE behavior |
|------------|----------------|--------------|
| 400 | Malformed request or missing required fields | Log error, surface to owner, action stays on HOLD |
| 401 | Missing or invalid credential | Emit GovernanceServiceUnavailable, action on HOLD |
| 403 | Valid credential but insufficient scope | Emit GovernanceServiceUnavailable, action on HOLD |
| 409 | Duplicate lee_request_id — already evaluated | Return original verdict reference if available |
| 422 | Valid request but policy pack version mismatch | LEE re-fetches expected policy version and retries |
| 429 | Rate limit exceeded | LEE waits Retry-After, then retries — action remains on HOLD |
| 500 | Internal CerbaSeal error | Emit GovernanceServiceUnavailable, action on HOLD |
| 503 | CerbaSeal temporarily unavailable | Emit GovernanceServiceUnavailable, action on HOLD |

**On any non-200 response:** LEE marks CerbaSeal as unavailable and places the action on HOLD. LEE will NOT execute the action. LEE surfaces the hold to the owner with a plain-language explanation. There is no silent fallback.

## What LEE Will Never Send

- **Secrets or credentials** — never in any field
- **Raw environment variable values** — LEE's constitutional constraint
- **Full memory database contents** — LEE sends scoped evidence references, not memory dumps
- **Requests for non-consequential actions** — reading, summarizing, drafting, and analyzing never go to CerbaSeal

---

## What LEE Records on Its Side

After every CerbaSeal call, LEE emits the following events into its own Event Log (CerbaSeal does not need to do anything for this — CerbaSeal's audit trail is authoritative on its side):

```
GovernedActionSubmitted      — lee_request_id, action_class, target_system, affected_project_id
GovernedActionAllowed        — lee_request_id, decision_id, authorization_expiry
GovernedActionHeld           — lee_request_id, decision_id, missing_approvals, remediation_requirements
GovernedActionRejected       — lee_request_id, decision_id, reason_codes
GovernanceEvidenceReceived   — lee_request_id, evidence_bundle_ref, audit_entry_ref
GovernanceServiceUnavailable — timestamp, error_summary, action_class (action placed on HOLD)
ExecutionReleased            — lee_request_id, decision_id, executed_at  (when ALLOW and execution completes)
ExecutionCancelled           — lee_request_id, reason  (when owner cancels an ALLOW before execution)
```

## Action Class Registry

The following `action_class` values are what LEE will use. CerbaSeal's policy pack should define rules for each class:

| action_class | Description | Example |
|-------------|-------------|---------|
| `EXTERNAL_COMMUNICATION` | Sending any message to someone outside LEE | Send email, post to LinkedIn |
| `EXTERNAL_DOCUMENT_SHARE` | Sharing a document with an external party | Share Google Drive file with investor |
| `REPOSITORY_MODIFICATION` | Any write action to a connected code repository | Merge PR, push commit, create issue |
| `DEPLOYMENT_CHANGE` | Triggering or approving a deployment | Deploy to production |
| `MEMORY_DELETION` | Deleting or overwriting important LEE knowledge objects | Delete a project, archive a fact |
| `FINANCIAL_TRANSACTION` | Any action involving money | Approve a payment, log an expense |
| `CANONICAL_STATUS_CHANGE` | Changing a project's official status | Mark project as inactive or archived |
| `CONNECTOR_PERMISSION_GRANT` | Granting a connector new permissions | Grant Google Drive write access |
| `SENSITIVE_DATA_EXPORT` | Exporting sensitive project data outside LEE | Export project facts to CSV |
| `INVESTOR_PARTNER_CONTACT` | Contacting an investor or pilot partner | Email pilot partner, book investor call |
| `CROSS_SYSTEM_WORKFLOW` | Executing a workflow in another Lamont Labs system | Trigger a CerbaSeal workflow from LEE |
| `PROVIDER_WRITE_ACTION` | Any write action through an external provider adapter | Post a calendar invite |

## What Does NOT Come to CerbaSeal

LEE routes the following through CIL or its own internal engines — they never reach CerbaSeal:

- Reading data from any provider
- Searching, summarizing, analyzing, or synthesizing
- Drafting content (a draft is not an action)
- Building context packets or generating internal briefs
- Identifying stale information or suggesting next actions
- Running internal background analysis
- Any read-only intelligence operation

## Policy Pack Versioning

LEE includes `policy_pack_version` in every request. This is the version LEE expects CerbaSeal to evaluate against. If CerbaSeal's active policy pack has changed and the version does not match, CerbaSeal should return `422` with `error_code: "POLICY_PACK_VERSION_MISMATCH"`. LEE will then re-fetch the current policy pack version, update its ServiceRegistry record, and resubmit.

CerbaSeal should expose a lightweight endpoint LEE can call to retrieve the current policy pack version:
```
GET /policy/current-version
→ { "policy_pack_version": "2026.7.1", "effective_from": "2026-07-01T00:00:00Z" }
```

This endpoint requires the same `govern:evaluate` credential — no additional scope needed.
